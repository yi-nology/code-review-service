# Review Service 扩展能力规划

## 1. 背景

Review Service 当前已经具备较完整的 AI 代码评审平台雏形，核心能力包括：

- 多平台接入：GitHub、GitLab、Gitea、GitCode、腾讯工蜂。
- AI 评审执行：基于 Open Code Review 和可配置 LLM。
- 多 Agent 工作流：支持不同审查视角并行执行、聚合和讨论。
- 会话与进度：支持评审会话、实时进度、历史追踪。
- 质量门禁：支持规则、评分、严重级别阈值和写回。
- Web 控制台：包含评审列表、详情、设置、诊断、项目报表、贡献者视图等。
- 运维辅助：健康检查、诊断快照、Webhook 和写回记录。

下一阶段不建议继续堆叠零散功能，而应围绕“评审可信度、企业落地、研发质量治理、生产可运维”四条主线演进，将项目从 AI Review 服务升级为研发质量治理平台。

## 2. 总体目标

### 2.1 产品目标

- 降低团队接入和日常使用成本。
- 提升 AI 评审结果的可信度、稳定性和可解释性。
- 建立问题发现、反馈、修复、趋势分析的闭环。
- 支持多团队、多项目、多人协作的企业级使用方式。

### 2.2 技术目标

- 增强任务执行可靠性，支持失败恢复、重试和诊断。
- 完善配置安全、权限边界和审计能力。
- 建立可观测指标体系，支撑生产环境运行。
- 控制 LLM 调用成本，并为不同项目提供可调策略。

## 3. 能力主线

## 3.1 评审可信度闭环

这是最优先的演进方向。当前系统已经可以发现问题和写回评论，下一步应让系统能够持续学习哪些结果有效、哪些是误报，以及问题是否真的被修复。

### 能力 1：Finding 反馈学习

目标：

- 支持用户对每条 Finding 标记“有效、误报、忽略、已修复、需要人工判断”。
- 记录反馈人、反馈时间、反馈原因和可选备注。
- 基于项目、规则、Agent、文件路径、问题类型统计误报率和有效率。

建议实现：

- 复用并扩展现有 `finding_feedback` 相关模块。
- 在评审详情页和 Session 详情页增加反馈入口。
- 后端增加反馈统计 API，供规则优化和项目报表使用。

验收标准：

- 每条 Finding 可被反馈并持久化。
- 项目维度可查看近 7/30/90 天有效率和误报率。
- 反馈数据可被规则权重或 Agent 策略读取。

### 能力 2：稳定 Finding ID 与问题生命周期

目标：

- 将跨多次评审中的同类问题识别为同一个问题。
- 区分“新增问题、历史遗留、已修复、重新出现”。
- 为项目质量趋势提供稳定口径。

建议实现：

- 基于 provider、repo、file path、rule/category、normalized message、code context、line range 等生成稳定指纹。
- 对不同 commit 中 line number 变化做弱匹配。
- 新增 Finding 生命周期表，记录首次发现、最近出现、修复时间、状态。

验收标准：

- 同一问题在连续评审中不会被重复统计为新增。
- 评审报告展示新增、存量、已修复数量。
- 项目报表可展示问题修复率和平均修复周期。

### 能力 3：建议补丁与自动修复

目标：

- 从“指出问题”升级到“辅助修复问题”。
- 支持单条 Finding 生成 patch、多条 Finding 批量生成 patch。
- 后续可扩展为创建修复分支和修复 PR。

建议实现：

- 扩展现有 `suggestion_patch` 能力。
- 对 patch 做安全校验：路径约束、上下文匹配、冲突检测、最大变更规模限制。
- 在前端提供 patch 预览、复制、应用、回滚入口。

验收标准：

- 高置信度 Finding 可生成建议 patch。
- patch 应用前可预览 diff。
- patch 应用失败时返回明确原因。

### 能力 4：模型与 Agent A/B 评估

目标：

- 用真实评审数据比较不同模型、不同 Agent 组合的效果。
- 找到质量、成本、耗时之间的最佳平衡。

建议实现：

- 扩展现有 `model_compare` 能力。
- 支持同一 PR 使用不同模型或 Agent 组合执行评审。
- 输出命中数量、严重问题、重复率、误报反馈、token、耗时、成本等对比指标。

验收标准：

- 用户可在 Review Detail 中发起模型对比。
- 对比报告包含质量、成本、耗时三类指标。
- 对比结果可沉淀为项目默认策略。

## 3.2 企业落地能力

该方向解决多人、多团队、多项目长期使用的问题。

### 能力 1：用户、角色与权限

目标：

- 从单一 `REVIEW_TOKEN` 演进为用户体系。
- 支持管理员、项目管理员、审查员、只读用户等角色。
- 控制项目访问、配置修改、发布写回、诊断查看等权限。

建议实现：

- 第一阶段可支持本地账号和 Token。
- 第二阶段接入企业 SSO、OIDC 或 LDAP。
- API 层统一增加权限校验中间件。

验收标准：

- 不同角色登录后看到的菜单和操作不同。
- 非授权用户不能访问或修改项目配置。
- 所有敏感操作可追溯到具体用户。

### 能力 2：组织与项目空间

目标：

- 支持多团队隔离。
- 将平台配置、规则包、Agent、项目策略、报表数据归属到组织空间。

建议实现：

- 引入 Workspace/Organization 模型。
- 现有 repo、policy、agent、platform token 等配置增加 workspace 归属。
- 前端支持空间切换。

验收标准：

- 不同空间的数据、配置和统计互相隔离。
- 用户可属于多个空间并拥有不同角色。
- 默认空间兼容已有单租户使用方式。

### 能力 3：配置审计

目标：

- 记录所有影响评审结果和安全边界的配置变化。
- 支持问题追溯和合规审计。

建议实现：

- 审计对象包括模型配置、OCR 配置、平台 Token、Webhook Secret、Agent、规则包、质量门禁、项目策略。
- 记录操作者、时间、对象、动作、变更摘要、变更前后版本。
- 前端增加审计日志页面。

验收标准：

- 关键配置变更全部生成审计记录。
- 管理员可按项目、用户、对象类型查询审计日志。
- 敏感字段在审计中必须脱敏。

### 能力 4：Secret 管理升级

目标：

- 统一管理平台 Token、LLM Key、Webhook Secret。
- 避免明文回显和误泄露。

建议实现：

- 数据库存储前加密。
- 前端只展示“已配置、未配置、最后更新时间、最后校验状态”。
- 支持连接测试、轮换提醒、失效检测。

验收标准：

- API 不返回 Secret 明文。
- Secret 更新、删除、测试均有审计记录。
- 平台连接失败时能给出明确诊断建议。

## 3.3 研发质量治理能力

该方向将系统从“评审工具”升级为“质量治理平台”。

### 能力 1：项目风险画像

目标：

- 识别高风险文件、模块、目录、问题类别和责任边界。
- 帮助团队判断质量治理优先级。

建议实现：

- 基于 Finding 生命周期、严重级别、出现频率、修复周期、代码 churn 构建风险分。
- 项目报表展示风险热力图、高风险文件列表、问题分类分布。

验收标准：

- 项目详情页展示 Top 风险文件和 Top 问题类型。
- 支持按时间范围、目录、作者、严重级别筛选。
- 风险分计算逻辑可解释。

### 能力 2：质量门禁趋势

目标：

- 观察质量门禁通过率和失败原因变化。
- 支持团队周会、复盘和治理目标追踪。

建议实现：

- 统计门禁通过率、失败 PR 数、失败原因、严重问题数量、平均评分。
- 按项目和时间维度生成趋势图。

验收标准：

- 项目报表支持查看 7/30/90 天质量趋势。
- 可以定位门禁失败的主要规则和问题类别。
- 趋势数据可导出。

### 能力 3：贡献者成长报告

目标：

- 以建设性方式帮助开发者了解常见问题和改进趋势。
- 避免只做简单排名。

建议实现：

- 基于个人 Finding 类型、修复率、误报反馈、质量趋势生成个人报告。
- 提供常见问题、改进建议、推荐学习主题。

验收标准：

- 贡献者详情页展示个人问题分布和趋势。
- 报告文案以改进建议为主，不以惩罚排名为主。
- 支持按项目和时间范围筛选。

### 能力 4：周期报告

目标：

- 自动生成周报、月报或发布前质量报告。
- 支持研发管理者快速掌握质量变化。

建议实现：

- 报告内容包括项目风险、Top 问题、修复率、门禁趋势、评审耗时、LLM 成本。
- 支持 Markdown、HTML、PDF 导出。
- 后续支持推送到飞书、企业微信、Slack、邮件。

验收标准：

- 用户可选择项目和时间范围生成报告。
- 报告可导出并保留历史版本。
- 报告中的关键指标可追溯到原始评审记录。

## 3.4 生产可运维能力

该方向保障系统接入真实研发流程后的稳定性。

### 能力 1：任务队列可靠性

目标：

- 提升 Webhook、评审任务、写回任务的可靠性。
- 支持失败恢复、重试和死信处理。

建议实现：

- 为任务增加状态机：pending、running、retrying、failed、dead、completed。
- 支持指数退避重试、最大重试次数、手动重放。
- 将不可恢复任务进入死信队列。

验收标准：

- 服务重启后未完成任务可恢复。
- 失败任务可以查看原因并手动重试。
- 重试不会导致重复写回或重复创建评审。

### 能力 2：全链路诊断视图

目标：

- 用户能快速回答“一次审查为什么失败”。
- 降低平台配置、Webhook、OCR、LLM、写回等问题排查成本。

建议实现：

- 在诊断页按 review_id 串联 Webhook 接收、payload 解析、任务创建、仓库克隆、diff 获取、OCR 执行、Agent 聚合、门禁判断、写回发布。
- 每个节点展示状态、耗时、错误摘要、建议动作。

验收标准：

- 每次 Review 都有可查看的执行链路。
- 失败节点有明确错误原因和下一步建议。
- 支持按 provider、repo、status、时间范围筛选。

### 能力 3：Prometheus 指标与告警

目标：

- 支持生产环境监控和容量规划。

建议指标：

- API 请求量、延迟、错误率。
- 评审队列长度、评审耗时、失败率。
- OCR/LLM 调用耗时、失败率、token 使用量。
- Webhook 接收数量、解析失败数量。
- 写回成功率、失败率、平台 API 延迟。
- Worker goroutine 数、数据库连接池状态。

验收标准：

- 提供 `/metrics` 端点。
- Grafana 可展示核心面板。
- 关键异常可配置告警阈值。

### 能力 4：LLM 成本控制

目标：

- 控制大规模接入后的模型调用成本。
- 为不同项目提供差异化策略。

建议实现：

- 按空间、项目、模型统计 token 和费用。
- 支持预算、用量上限、超额降级。
- 大 PR 自动采用“摘要优先 + 重点文件精评”策略。
- 低风险变更可走轻量模型或规则评审。

验收标准：

- 项目报表展示 token、成本和模型分布。
- 可配置项目级预算和超额行为。
- 大 PR 评审成本可解释、可追踪。

## 4. 阶段计划

## Phase 1：可信度闭环与诊断增强（1-2 周）

优先级最高，投入较小，能显著提升用户信任。

范围：

- Finding 反馈学习。
- 稳定 Finding ID。
- 新增/存量/已修复识别。
- Review 执行链路诊断增强。

交付物：

- Finding feedback API 与前端交互。
- Finding fingerprint 生成和生命周期存储。
- Review Detail 中展示问题生命周期。
- Diagnostics 中支持按 Review 查看链路。

关键指标：

- 用户可对 100% Finding 做反馈。
- 同类问题跨评审重复识别准确率达到可用水平。
- Review 失败原因可定位到具体阶段。

## Phase 2：自动修复与质量报表（2-4 周）

范围：

- 建议 patch 升级。
- 模型与 Agent A/B 对比。
- 项目风险画像。
- 质量门禁趋势。
- 周期报告导出。

交付物：

- Patch 预览、应用、失败回滚。
- 模型对比报告页面。
- 项目质量趋势页增强。
- Markdown/HTML 报告导出。

关键指标：

- 高置信度 Finding 可生成 patch。
- 项目维度能展示趋势、风险文件、Top 问题类型。
- 用户可生成指定时间范围的质量报告。

## Phase 3：企业级多团队能力（4-6 周）

范围：

- 用户、角色、权限。
- 组织/空间隔离。
- 配置审计。
- Secret 加密存储与轮换。

交付物：

- 用户登录和角色管理。
- Workspace 模型与空间切换。
- 审计日志页面。
- Secret 管理升级。

关键指标：

- 不同团队可隔离使用。
- 敏感操作全部可审计。
- Secret 不再通过 API 明文回显。

## Phase 4：生产化与规模化（持续建设）

范围：

- 持久化任务队列。
- 死信队列与手动重放。
- Prometheus 指标与 Grafana 面板。
- LLM 成本控制。
- 企业通知集成。

交付物：

- 任务状态机和重试机制。
- `/metrics` 指标端点。
- 成本报表和预算配置。
- 飞书、企业微信、Slack、邮件通知。

关键指标：

- 服务重启后任务可恢复。
- 评审和写回失败可重试。
- 管理员可查看成本和容量趋势。

## 5. 推荐优先级

如果只能选择最值得先做的 5 项，建议顺序如下：

1. Finding 反馈学习闭环。
2. 稳定 Finding ID 和问题生命周期。
3. 全链路诊断视图。
4. 建议 patch 与自动修复。
5. 项目质量趋势和周期报告。

这 5 项完成后，系统将具备更清晰的产品价值闭环：发现问题、确认问题、修复问题、追踪趋势、持续优化。

## 6. 风险与注意事项

- AI 评审结果不能只追求数量，应重点控制误报率和解释质量。
- 自动修复必须做严格边界控制，避免越权修改、路径逃逸和误应用 patch。
- 权限体系和 Workspace 改造会影响较多数据模型，应分阶段兼容现有单租户模式。
- Secret 加密、审计日志、任务重试属于基础设施能力，设计时要避免只服务当前页面流程。
- 报表指标必须保持口径稳定，否则趋势图会失去可信度。

## 7. 后续落地建议

建议下一步先拆出 Phase 1 的工程任务：

- 设计 Finding fingerprint 字段和生命周期表。
- 扩展 feedback API 和前端反馈组件。
- 在 Review 执行流程中记录阶段事件。
- 在 Diagnostics 页面增加 Review 链路视图。
- 为 Finding 生命周期和反馈统计补充单元测试。

完成 Phase 1 后，再进入自动修复和质量报表建设。这样路线稳，收益也会比较快显现。
